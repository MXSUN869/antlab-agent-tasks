# 挑战 B：缓存故障区分实验

## 实验目的
区分缓存键不完整与检索/范围处理错误这两种可能原因。

## 时间顺序说明
R01/R02 的原始异常已经在 baseline.json 中观察到。
以下假设和预测是回顾性提出，不能视为基线运行前的预注册预测。

## 基线的可复现性（2026-10-15 补充）
`runs/baseline.json` 是用**题包原件的** `challenge:Engine` 跑出来的，二者逐字段一致
（7/7 用例）。工作副本中的 `challenge.py` 一度被改过（缓存键加入了 doc_ids/snapshot/k，
把本节的预埋故障改掉了），导致基线无法复现；已按题包原件归位，
现哈希与 `进阶/文件校验.json` 一致。核对过程见 `pack_integrity.md`。
因此本节实验一、实验二都能被评委用以下命令原样重放：

```bash
python 进阶/challenge_b/run_cases.py --engine challenge:Engine --output <临时文件>
```

## 假设 A：缓存键不完整
预测：全新 Engine 单独执行 R02 时，cache_hit 为 false，
并按 alpha/v2 的范围返回 b02，而不是 b01。

## 假设 B：检索/范围处理本身出错
预测：全新 Engine 单独执行 R02 时，即使没有缓存，
仍可能返回错误版本、错误证据或空证据。

## 干预设计
对照一：新 Engine 只执行 R02。
对照二：另一个新 Engine 先执行 R01，再执行 R02。

## 执行前记录
以上为待检验预测，实际结果将在实验运行后追加。

## 实验结果（2026-10-14）

### 实验一：新引擎单独运行 R02
- cache_hit: false
- answer: 请求超时阈值为12秒。
- evidence: b02
- locator_status: valid
- status: ok

### 实验二：同一引擎先运行 R01，再运行 R02
- R01: cache_hit=false，答案为30秒，证据为b01。
- R02: cache_hit=true，答案仍为30秒，证据仍为b01。

### 结果解释
新引擎单独运行 R02 时能够返回 alpha/v2 的 b02。
同一引擎先运行 R01 再运行 R02 时，R02 复用了旧结果。
实验结果支持缓存键未区分文档版本这一解释。

### 结论边界
该实验支持缓存复用导致本次跨版本错误。
它不证明检索系统没有其他缺陷；R03 的范围筛选问题需要独立处理。

## 等价变体测试记录

### 测试目的

验证查询大小写和 `doc_ids` 列表顺序变化是否影响检索结果及缓存行为。

### 实际结果

| 变体 | Evidence | Locator | Cache hit | Status |
|---|---|---|---|---|
| 原始请求 | b05 | valid | False | ok |
| 查询改为大写 | b05 | valid | True | ok |
| 反转 doc_ids 顺序 | b05 | valid | True | ok |

### 结论

三个请求均返回 b05，定位状态一致。大小写规范化和文档 ID 排序使语义等价请求可以复用缓存结果。在本测试输入下，结果一致性得到验证；这不代表所有查询或文档范围组合都已验证。

> 补充（事后复核，2026-10-15）：上表由两个引擎分别复跑得到，数值完全相同。
> 但**两个引擎"命中"的原因不同**，这一点对结论很重要：
>
> - **原始样机**的缓存键只有 query。V2 命中是因为大小写已被同一化；
>   V3 命中是因为 `doc_ids` **根本不参与键**。也就是说，它"能复用等价输入"
>   是缓存键过窄的副产品，与 R02 的跨版本污染**同一个根因**。
> - **修复版**把 `request` 按 `spec.md` 第 2、3 条的语义规范化（query 去空白并小写、
>   doc_ids 去重并排序）后，连同 `corpus`/`draft` 一起纳入键。因此 V2/V3 仍然命中，
>   而跨 snapshot 的请求不再命中。
>
> 结论：修复**没有**用"关闭缓存复用"换安全，而是把"该复用的继续复用、
> 不该复用的不再复用"这两半同时做到。两个引擎的完整对照与预期依据见
> `regression_and_variants.md` 第三节。

## 自建边界案例记录

### 测试输入

查询：metadata beta
文档范围：beta
请求快照：v999（数据中不存在）

### 实际结果

- evidence：空列表
- locator_status：invalid
- support_status：not_checked
- status：ok

### 结论

系统没有将其他快照的 b05 作为当前请求的有效证据，但整体状态仍为 ok，没有明确区分正常完成与无可用证据的情况。

该案例记录为尚未解决的边界风险。本次工作重点是缓存跨版本污染，因此暂不将该问题描述为已修复。

> 补充（事后复核，2026-10-15）：修复版在同一输入下把 `status` 从 `ok` 改为
> `invalid_scope`，跨快照回退依然为否。但 `spec.md` 第 3 条要求的
> "引用缺失与引用越界分别标识"只实现了三态（`missing`/`invalid`/`valid`），
> 尚无专门用例固定；`scoped` 非空但正分证据为空时仍返回 `ok`。
> 这两项仍在 `regression_and_variants.md` 第四、五节登记为未解决。
