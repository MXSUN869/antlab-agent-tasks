# 失败索引与输出截断诊断

对应题目第三步「确认实际 messages 和段落 ID、原文、顺序与清单一致」之后的失败复核，
以及第四步「首次技术失败、格式错误和无答案均保留在分母」和第五步「查一个其他原因」。

数据源：`runs/*.json` 原始日志（经 `starter/build_main_results.py` 重建为
`main_runs_40.csv` 与 `retry_runs_main.csv`）。**本文只重读日志，不调用模型。**

> **命名提醒（重要）**：文件名里的 `retry` 与本文标题里的「重试」指的是
> **2026-10-14 用改后提示词做的第二次整批执行**，不是同条件重复测量。
> 冻结的 40 次主结果用的是另一版 `student.py`。逐版本的对应关系见
> `frozen_version.md`，本文第四节专门说明它对本页结论的影响。

## 二、两种截断形态，以及它们的共同原因

### 形态 A：推理吃满全部输出预算，答案一个字符都没生成（13 条）

这 13 条的 `usage` 完全一致：

```
completion_tokens = 1024   (== config.parameters.max_tokens)
reasoning_tokens  = 1024   (== completion_tokens)
finish_reason     = "length"
content           = ""     （message.content 为空字符串）
```

本次使用的模型是**带推理内容的模型**：响应的 `choices[0].message` 同时有
`reasoning_content` 与 `content` 两个字段，而 `usage.completion_tokens_details.reasoning_tokens`
记录了推理部分占用的 token 数。

**因此机制是确定的：`max_tokens=1024` 是「推理 + 正文」的共享预算，
13 次请求的推理部分独自耗尽了这个预算，正文没有任何配额，于是 `content` 为空。**

这不是传输错误：这些记录的 `status=ok`、`http_status` 正常、`response` 完整、
`usage` 完整。**API 调用成功并不等于产生了可用的答案**——这正是题目要求区分的一点。

这 13 条分布在两个提示词版本上（冻结版 8 条、10-14 版 5 条），
因此该机制不是某一次提示词写法的产物。

### 形态 B：正文写了一半被切断（1 条）

`T01 / R0 / retry_2`（`run_id=d5679737-dee3-48dd-91ab-48d01d231652`）：

```
max_tokens        = 512      ← 全部 81 条记录里唯一一次参数偏离
completion_tokens = 512
reasoning_tokens  = 494
finish_reason     = "length"
content           = {"answer":"S24","citations":["P555495","P761989
```

正文确实开始了，但在写完 JSON 之前预算就用完了。**这一条被单独列出，
因为它的生成参数与其余 80 条不一致。**

## 三、与机制一致的旁证（只作提示，不作独立实验）

T01 / R0 baseline 在同一用例上有三次尝试，`max_tokens` 分别为 1024、512、1024：

| 尝试 | 版本哈希 | `max_tokens` | `reasoning_tokens` | 正文结果 |
|---|---|---|---|---|
| 首次 | `893e1e16…`（冻结） | 1024 | 1024 | 完全为空 |
| retry_2 | `0521934d…` | **512** | 494 | 写出 18 个 token 后被切断 |
| retry_3 | `3a8c56bb…` | 1024 | 610 | 完整，得到 `{"answer":"S24","citations":["P555495","P761989"]}` |

把共享预算从 1024 降到 512 时，截断点从「正文起点之前」前移到「正文中途」——
形态 A 变成了形态 B，与「预算由推理与正文共享」这一解释一致。

**但这条证据是打了折扣的**：三次尝试分属三个不同的 `student.py` 版本，提示词也随之改写过，
所以 `max_tokens` 并非唯一变化的变量。因此这里只把它当作**与机制一致的旁证**，
不声称它构成一次干净的对照实验。机制本身的依据是第二节的 `usage` 读数。

## 四、第二次整批执行说明了什么、不说明什么

**事实**：2026-10-14 用**改写过的提示词**（`student_sha256 = 3a8c56bb…`）把评测题整批重跑了一遍，
共 41 条。它与冻结的 40 次主结果**不是同一输入**（`messages` 逐条都不同，见 `frozen_version.md`）。

| 首次失败的用例 | 10-14 第二次执行结果 | 该次的 `reasoning_tokens` |
|---|---|---|
| T01 R0 baseline | ✅ 合法 JSON，答案 S24 | 610 |
| T01 R1 baseline | ✅ 合法 JSON，答案 S24 | 577 |
| T01 R2 baseline | ✅ 合法 JSON，答案 S24 | 565 |
| T04 K baseline | ✅ 合法 JSON，答案「证据不足」 | 441 |
| T06 K baseline | ✅ 合法 JSON，答案 25% | 393 |
| T08 K baseline | ✅ 合法 JSON，答案「证据不足」 | 917 |
| T08 R0 improved | ❌ 再次截断（1024/1024） | 1024 |
| T07 K baseline | ❌ 再次截断（1024/1024） | 1024 |

**能说明的**

1. 截断**不是某一次提示词写法的偶发产物**：换了一版提示词后整批重跑，41 条里仍有 **5 条**截断
   （占 12.2%），且 T08/R0 improved 与 T07/K 在两个版本下都失败。
2. 失败与题目的关系是可观察的：K 条件（只给 2 段资料）的截断率在两个版本里都最高。

**不能说明的**

1. **不能**说「同一请求会随机地在成功与截断之间翻转」——那需要同输入重复，
   而这 41 次用的是改后的提示词，与主结果不同输入。原先的这一说法已在此撤回。
2. **不能**用这 41 次的结果去修正 40 次主结果的数字。主结果保持冻结版本的原值，
   这 41 条按题目要求标注为**冻结后的追加探索**，单独存放于 `retry_runs_main.csv`。

**版本之间的可比性**（供评委判断这 41 条能不能与主结果并列）：

| 项目 | 冻结版 40 条 | 10-14 版 41 条 | 是否一致 |
|---|---|---|---|
| 模型 | `deepseek-v4-1-flash-260910` | 同 | ✅ |
| `temperature` | 0 | 0 | ✅ |
| `timeout_seconds` | 90 | 90 | ✅ |
| `max_tokens` | 1024（40/40） | 1024（40/41）、512（1/41） | ⚠️ 1 条不同 |
| `student_sha256`（提示词 + 实现） | `893e1e16…` | `3a8c56bb…`（+1 条 `0521934d…`） | ❌ **不同** |
| `data_sha256` | 单一取值 | 单一取值，与冻结版相同 | ✅ |

## 五、必须写明的参数与版本不一致

题目要求「统一模型、提示词、生成参数和判分口径；无法统一的差异写明」。逐条核对后：

**40 次主结果内部完全一致**：`provider`、`endpoint` 主机、`model`、`temperature`、
`timeout_seconds`、`max_tokens`、`student_sha256`、`data_sha256` 各自都只有一个取值。

**与第二次执行之间的差异**：

| 差异项 | 说明 |
|---|---|
| `student_sha256` | 主结果 `893e1e16…`；第二次执行 `3a8c56bb…`（另有 1 条 `0521934d…`）。提示词被改写过 |
| `max_tokens` | 主结果 40/40 为 1024；第二次执行有 1 条为 512（`T01/R0/baseline/retry_2`，`utc=2026-10-14T03:21:45Z`） |

这两项差异的成因、范围与对结论的影响见 `frozen_version.md` 与本文第四节。

## 六、代价与未验证的部分

**代价**

- 8 次主结果（占 20%）因截断无法评分，按题目要求计入分母而非剔除，
  因此 `condition_comparison.csv` 中 R0/R1/R2 的准确率为 7/8 = 87.5%、K 为 4/8 = 50.0%。
  若只看技术成功后的结果，五组的条件准确率都是 100%（见 `accuracy_valid_only` 列）。
  **两个口径必须同时给出**：只看后者会把技术失败掩盖成「模型都答对了」。
- 截断的 13 条各消耗了 1024 个输出 token 却没有产出，属于直接浪费的额度。
- 截断请求的客户端耗时反而偏高（6.7–9.0 秒），因此**耗时数据里混入了「生成到一半被砍」的样本**，
  这正是不能把耗时直接与答案质量一起解读的原因。

**未验证**

- **没有测**如果放宽输出上限，这些题会不会被答对。按已记录的决策（见 `decisions.md` D3），
  正式实验冻结后不追改生成参数，因此本项**未做**，属于已知的未完成部分。
- 服务端为什么在第 90 百分位处出现长推理（是题目本身需要跨段比较，还是与 K 条件下资料不足有关）
  **没有机制级证据**。可观察的相关性是：K 的截断率（4/8，第二次执行里仍是最高）明显高于三种全文顺序，
  而 K 的有效输出全部是「证据不足」——这与「资料不足时模型在推理里反复查找」相符，
  但**这只是相关，不是因果**，本轮没有做能区分这一解释的实验。
- 由于 41 条第二次执行与主结果不是同一输入，**本轮没有同条件的重复测量**，
  因此关于「输出长度是否随机」本页不作任何主张。
